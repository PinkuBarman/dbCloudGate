dbCloudGate — Enterprise Tech-Stack Decision Guide

Languages & GCP services · decision trees, comparisons and recommendations · draft for review

This guide works each major build decision as a short decision tree (what to pick given your constraints), a side-by-side comparison, and a recommended default. The green rows and callouts are the recommendation for an enterprise, regulated deployment; alternatives are valid where the noted condition applies. Once you finalise the picks, they fold into the build-plan document.

1Front-end language & framework

Purpose in dbCloudGateThis is what a person actually uses — the onboarding wizard, the readiness score, the cost and blueprint screens, the architecture diagrams and the generated SDD. It turns the whole process into a guided set of screens instead of spreadsheets and emails.
A single-page app that renders the wizard, tables and diagrams. The choice is mostly about ecosystem and your org's existing standard.
OptionBest whenTrade-offs
React + TypeScriptRecommendedYou want the largest component ecosystem, easiest hiring, and freedom to adopt any design system.Unopinionated — you assemble routing/state libraries yourself.
AngularAltYour org already standardises on Angular; you want an opinionated, batteries-included framework.Steeper learning curve; heavier.
VueSmall team wanting a gentle learning curve.Smaller enterprise footprint / hiring pool.
RecommendationReact + TypeScript, unless your organisation already standardises on Angular — in which case use Angular to reuse skills and shared libraries.

2Core back-end language

Purpose in dbCloudGateThe engine behind those screens. It remembers each application’s request, enforces the gate rules (for example, it won’t let a CR be raised while a blocker is open), talks to Confluence, Jira and the CMDB, and keeps the audit trail. The “brain and plumbing” of the platform.
The workflow engine, CR/approval logic and integration services. The AI work is deliberately a separate Python service (section 3).
Decision tree — core service language
OptionBest whenTrade-offs
Java 21 + Spring BootRecommendedEnterprise/regulated shop; you value mature security libraries, strong typing and a deep hiring pool.Heavier runtime; mitigate cold starts with CRaC or GraalVM native image.
GoAltYou want lean images, fast cold starts and strong concurrency, and have Go skills.Smaller enterprise dev pool; fewer batteries-included frameworks.
Node.js + TypeScriptYou want to unify with the front end and move fast on a smaller team.Less ideal for CPU-heavy work and very large domain models.
RecommendationJava 21 + Spring Boot for the core services in a regulated enterprise. Choose Go if lean, fast-starting services matter more and the team has Go depth. Keep one house language for the core; don't spread across three.

3AI / document-intelligence service language

Purpose in dbCloudGateThe part that does the reading and thinking. It ingests the uploaded architecture documents, pulls out the technical profile, maps each current component to a GCP target, scores readiness and drafts the SDD — the capability the prototype shows as the “analysing” and typewriter steps.
Extraction, mapping, scoring and SDD drafting — a distinct microservice so its dependencies and scaling are isolated from the core.
OptionBest whenTrade-offs
Python + FastAPIRecommendedAnything touching Document AI, Vertex AI, embeddings or RAG frameworks — richest, first-class SDKs.Not for high-throughput transactional APIs (that's the core service's job).
Java / Node clientsYou want the LLM calls in the core language and only use simple REST calls.Thinner ecosystem for RAG/eval tooling; more glue code.
RecommendationPython + FastAPI as an isolated AI microservice the core calls over REST/gRPC. This keeps model/SDK churn away from your core services and gives you the best RAG and evaluation libraries.

4Compute / hosting platform

Purpose in dbCloudGateWhere all of the above actually runs. It keeps the services online, scales them up when many teams onboard at once, and costs little when idle — so you are not managing servers.
Where the containers run. Favour the most-managed option that meets the requirement.
Decision tree — compute platform
OptionBest whenTrade-offs
Cloud RunRecommendedStateless containerised services (UI, APIs, AI service). Autoscales to zero, minimal ops.Request cap; less control over networking/mesh; not for stateful workloads.
GKE AutopilotAltYou need a service mesh, sidecars, long-running processes, or many tightly-coupled services.Cluster/ops overhead and cost even in Autopilot.
Cloud Functions (2nd gen)Small, single-purpose event handlers (Pub/Sub, Storage triggers).Not suited to full applications.
RecommendationCloud Run for every service. Reach for GKE Autopilot only when a concrete need appears (mesh, long-running jobs, sidecar-heavy patterns). Use Cloud Functions for glue event handlers.

5Data stores

Purpose in dbCloudGateThe platform’s memory. Every request, gap, approval, Change Request, uploaded document and generated SDD is stored here, so nothing is lost, the audit trail is complete, and portfolio reporting is possible.
Transactional workflow state, flexible request/session state, and analytics/reporting are three different jobs — use the right tool for each.
Decision tree — primary relational store
OptionBest whenTrade-offs
Cloud SQL (PostgreSQL)RecommendedTransactional workflow, CR and approval data. Managed, HA, cost-effective.Regional; vertical scaling limits (fine for this workload).
AlloyDB for PostgreSQLAltPostgres-compatible but you need higher performance or larger scale / mixed analytics.Higher cost than Cloud SQL.
Cloud SpannerGlobal, multi-region, horizontally-scaled strong consistency.Overkill and pricier for a single-region internal tool.
FirestoreFlexible/real-time request & session state, event-driven UI updates.Not for complex relational queries — use alongside, not instead of, SQL.
BigQueryPortfolio reporting, analytics, audit-scale querying.Analytical, not transactional.
RecommendationCloud SQL for PostgreSQL as the system of record, Firestore for flexible/real-time state, and BigQuery for reporting. Move the relational store to AlloyDB only if you outgrow Cloud SQL; Cloud Storage holds uploaded docs and generated artifacts.

6Workflow orchestration

Purpose in dbCloudGateThe traffic controller for the step-by-step lifecycle (readiness → demand → approval → design). It runs the steps in the right order, pauses while it waits for a Domain Lead approval or a background job, and stops anything from skipping a gate.
Driving the gated lifecycle (readiness → demand → approval → design) and the async work behind each step.
Decision tree — orchestration
OptionBest whenTrade-offs
Cloud WorkflowsRecommendedServerless step orchestration across GCP services and HTTP APIs for the gated flow.Not ideal for very long-running (months) human waits with complex compensation.
Pub/Sub + Cloud TasksAltEvent fan-out and reliable async/retryable work behind steps.You build the state machine yourself — pair with Workflows, don't replace it.
Temporal (on GKE / Temporal Cloud)Durable, long-running human-in-loop flows with rich compensation/rollback.Additional platform to run and operate.
Cloud Composer (Airflow)Scheduled data/ETL pipelines expressed as DAGs.Heavyweight for app workflow; it's a data-pipeline tool.
RecommendationCloud Workflows for the lifecycle transitions with Pub/Sub + Cloud Tasks for async work. Adopt Temporal only if approval waits and compensation logic become genuinely long and complex. Keep Composer for data pipelines, not app flow.

7API management & edge

Purpose in dbCloudGateThe secure front door to the platform’s APIs. It checks who is calling, blocks attacks, applies rate limits, and — with Apigee — lets other internal teams safely consume dbCloudGate’s services.
OptionBest whenTrade-offs
ApigeeRecommendedEnterprise API governance: quotas, security, analytics, a developer portal, exposing APIs to other teams.Cost; more to operate.
API GatewayAltInternal-only, lighter needs in front of Cloud Run / Functions.Fewer governance/analytics features than Apigee.
Front everything with the global external HTTPS Load Balancer + Cloud Armor (WAF) and Identity-Aware Proxy regardless of the gateway choice.
RecommendationApigee if the platform's APIs will be governed/exposed enterprise-wide; API Gateway if it stays internal and you want the lighter, cheaper option.

8Foundation model & retrieval (RAG)

Purpose in dbCloudGateThe actual AI “brain” that powers the extraction, recommendations and SDD text, plus the grounding library that makes it cite your real ADRs and blueprints instead of inventing references.
The GenAI core. Build a thin model-abstraction layer so you can route per task and swap models without touching business logic.
Decision tree — foundation model
OptionBest whenTrade-offs
Gemini on Vertex AIDefaultNative GCP integration, multimodal, long context, data stays in your GCP boundary.—
Claude on Vertex (Model Garden)Task pickStrong long-form reasoning & document drafting — extraction and SDD generation.Route per-task via the abstraction layer.
Open models (Gemma / Llama)You need self-hosting for cost/control and can accept quality/ops trade-offs.You own tuning, serving and evaluation.
Retrieval / grounding
OptionBest whenTrade-offs
Vertex AI SearchRecommendedFastest managed RAG over the ADR/blueprint/ERI corpus with connectors and ranking.Less control over chunking/ranking internals.
Vertex AI Vector SearchAltYou need custom embeddings, chunking and ranking pipelines.You build and operate the pipeline.
RecommendationPut a model-agnostic interface in the Python AI service. Default to Gemini for native integration; route to Claude for extraction and SDD drafting. Ground everything with Vertex AI Search so recommendations cite real ADRs/blueprints — never fabricated ones.

9Infrastructure-as-Code & CI/CD

Purpose in dbCloudGateHow the platform itself is built and shipped — repeatably and safely. The whole environment is defined as code with automated build, test and controlled deployment, so releases are consistent and auditable.
Infrastructure as code
OptionNotes
TerraformRecommendedDe-facto GCP standard, mature provider, multi-cloud, huge module ecosystem.
Config Connector / KRMKubernetes-native infra — sensible only if you go all-in on GKE.
Deployment ManagerDeprecated — avoid.
CI / CD
OptionNotes
Cloud Build + Cloud DeployRecommendedGCP-native build & progressive delivery; pairs with Binary Authorization.
GitHub Actions / GitLab CIAltUse if that's your org's SCM/CI standard; still deploy via Cloud Deploy.
RecommendationTerraform for all infrastructure. For CI/CD, use your org's existing SCM/CI (often GitHub/GitLab) for build and test, with Cloud Deploy for progressive delivery and Binary Authorization enforcing signed images. Greenfield? Cloud Build + Cloud Deploy end-to-end.

10Security, networking & observability

Purpose in dbCloudGateThe guardrails and the eyes. It keeps the sensitive architecture documents protected, controls exactly who can access what, and lets you see, alert on and troubleshoot everything the platform does.
These are largely non-optional for a regulated deployment — listed for completeness rather than as a choice.
AccessIdentity-Aware Proxy + Identity PlatformZero-trust access, corporate SSO via Workload Identity Federation.
AuthorisationIAM (least privilege) + Org PolicyFine-grained roles; guardrails at the org level.
Data protectionVPC Service Controls · Cloud KMS/CMEK · Cloud DLPExfiltration perimeter, customer-managed keys, PII scanning of uploads.
Secrets & supply chainSecret Manager · Binary Authorization · Artifact RegistryNo secrets in code; only signed, scanned images run.
PostureSecurity Command Center · Cloud Audit LogsContinuous posture management and a complete audit trail.
NetworkingShared VPC · Serverless VPC Access · Private Service Connect · Cloud NATPrivate egress to Confluence/Jira/CMDB; no public data paths.
ObservabilityCloud Monitoring · Logging · Trace · Error ReportingSLOs per service; alerting on failures and cost anomalies.
